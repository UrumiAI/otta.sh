# Otta MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let an admin or developer run an Otta store from an AI agent over MCP, with the same guards as the admin UI and no change for sites that don't opt in.

**Architecture:** First, five no-behaviour-change PRs move each admin write's guards out of the Block Kit handlers into plain `operations/*` functions that return typed outcomes. The handlers render those outcomes as they do today. Then a new package, `@urumi.ai/otta-mcp`, wraps the Otta plugin object (`withMcp`). From one tool table it adds JSON-POST routes and `mcp.tools` that call the same operations. EmDash's built-in `/_emdash/api/mcp` serves them as `otta__<name>`.

**Tech Stack:** TypeScript (strict), pnpm workspace, tsdown, vitest, zod (EmDash's), EmDash 1.5.0 plugin API, Playwright e2e.

**Spec:** `docs/superpowers/specs/2026-11-17-otta-mcp-design.md`. Read it first; this plan argues from it.

## Global Constraints

- Follow repo `CLAUDE.md`: TDD, money as integer minor units, no mocks of storage (real SQLite/Postgres test stores), tabs (`pnpm format`), `.js` internal imports, `import type` for types.
- **Step 1 PRs change no behaviour.** No existing test may be edited to pass. If one has to change, the extraction is wrong.
- Each PR branches from fresh `origin/main` in its own worktree `../otta-wt-<slug>`, gets the `[Plugin]` tag, uses merge commits only, and merges only when green with the run output in the PR body. One PR merges before the next starts.
- Before every PR: `pnpm lint && pnpm format:check && pnpm typecheck && pnpm -r build && pnpm test`, and `OTTA_E2E_START_STACK=1 pnpm test:e2e`. PRs touching packages/ also run `pnpm test:pack-types`.
- Commits are authored by the operator identity with **no AI attribution lines** (global hooks enforce it).
- Every MCP tool route: `permission: "plugins:manage"`, non-public, `request: { method: "POST", body: "json" }`, JSON response.
- Never read a payment secret back. `settings_get` reports only `set` / `not set`.
- Destructive tools (`destructive: true`): `orders_cancel`, `orders_refund`, `orders_revoke_download_access`, `coupons_retire`, `coupons_delete`, every `*_delete`, `payments_set_secret`, `payments_clear_secret`, `payments_cod_set_enabled`.
- Plugin id / tool prefix: `OTTA_PLUGIN_ID` (`otta`) → `otta__<name>`.

## Review Focus

1. **An agent retries a refund after a timeout, with the same inputs.** It must answer "already refunded" and never refund twice. (Task 1a pins it on the operation; Task 6c pins it through the MCP route.)
2. **An agent sends a partial `coupons_update`** (only `maxUses`). The start and end dates, minimum spend and other fields must be kept. (Task 6d test.)
3. **An agent calls `settings_update_currency` with no `confirm` while priced products exist.** It must get `needs_confirmation` with the product count, and nothing may change. (Task 1e + Task 6f.)
4. **The tool list changes after an admin has consented.** EmDash hides all Otta tools until consent is given again. That's documented in the README, not "fixed". (Task 6g README line.)
5. **A token without scope `mcp:tools:otta`, or a non-admin user,** must be refused with `INSUFFICIENT_SCOPE` or `INSUFFICIENT_PERMISSIONS`. (Task 6h integration test.)

## Phase 1 — extract admin operations (5 PRs, no behaviour change)

**The recipe every task 1a–1e follows:**
1. **Pin it.** Add characterization cases to the area's existing dispatch test file (named per task). They drive the real `dispatch…Action` / page handler over the real test store and assert the exact `Notice` title and variant for every outcome listed in the task. Run them on **unchanged** code: they must pass. Commit (`[Test] pin <area> admin outcomes`).
2. **Test the operation.** Write `packages/plugin/test/admin-operations-<area>.test.ts` calling the new operation directly. It asserts the outcome `kind` for the same cases. Run it: it fails (module missing).
3. **Extract.** Create `packages/plugin/src/admin/operations/<area>.ts`. Move the *decision* part (parse-free typed input → re-reads/guards → surface call → outcome) out of the handler. Leave the handler as `read payload → operation → noticeFor(outcome)`, with every notice string unchanged and staying in the handler file.
4. **Verify.** Run both test files plus the area's sandbox test. All pass, with no existing test edited.
5. **Export.** Add the operation and its types to `packages/plugin/src/admin/operations/index.ts`, and re-export from `packages/plugin/src/index.ts` under `// admin operations (MCP)`.
6. Run the full battery, commit, open the PR, record the run, merge.

```ts
// tool.ts
export interface McpToolDef<I extends z.ZodTypeAny> {
  name: string;               // snake_case, unique; becomes otta__<name>
  description: string;        // for agents: what it does, when to use it, units ("minor units, e.g. 1999 = $19.99")
  input: I;
  destructive?: boolean;
  run(args: { ctx: PluginContext; clients: AdminClients; input: z.infer<I>; operator: string | undefined }): Promise<unknown>;
}
export function defineTool<I extends z.ZodTypeAny>(def: McpToolDef<I>): McpToolDef<I>;
// errors.ts
export class ToolError extends Error { constructor(readonly code: string, message: string, readonly details?: unknown) }
export function toolFailure(code: string, message: string, details?: unknown): never;
// with-mcp.ts
export const MCP_ROUTE_PREFIX = "mcp/";
export function withMcp(plugin: SandboxedPlugin, tools?: readonly McpToolDef<z.ZodTypeAny>[]): SandboxedPlugin; // default tools = OTTA_MCP_TOOLS
```
`withMcp` returns a **new** object: `routes` = original routes plus, per tool, `"mcp/<name>": { public: false, permission: "plugins:manage", request: { method: "POST", body: "json" }, handler }`, and `mcp.tools[<name>] = { description, route: "mcp/<name>", input, destructive }`. The handler parses `routeCtx.input` with `def.input` (a failure throws `ToolError("INVALID_INPUT", …)`), builds `makeAdminClients(ctx)`, sets `operator` from `routeCtx.user` the way `admin-route.ts` does, and returns `run`'s value. A `ToolError` returns the error envelope EmDash's plugin-route contract uses for a failed route, with `code` preserved. It must throw if a tool name collides with an existing route.
