# 0.2.0 release notes

0.2.0 of the seven `@urumi.ai/otta-*` packages (`domain`, `plugin`, `store-emdash`,
`admin-react`, `admin-presentation`, `payments-stripe`, `payments-cod`) and of
`@urumi.ai/otta-store` was published to npm on 2026-11-09. `otta-payments-cod` and `otta-store`
are new in 0.2.0: they have no 0.1.0. There is no CHANGELOG (removed in #451); this file keeps
the notes that were asked for in pull requests and issues, so they are not lost when those
close. It lists what an upgrade from 0.1.0 can break, and what a running store sees.
`@urumi.ai/otta-plugin@0.1.0` is deprecated on npm: "Leaks build environment values into the
bundle. Upgrade to 0.2.0."

## Breaking for `@urumi.ai/otta-domain` consumers

- **Domain diagnostics go through an injected `logger`, and it is required.** 0.1.0 wrote them
  straight to `console`. In 0.2.0 `logger: Logger` is a required field of these deps types
  (#655, #665):
  - `CartDeps`, `QuoteDeps`, `CreateOrderDeps`, `ExpireOrdersDeps`;
  - `CancelOrderDeps`, `CancelOrderWithRefundDeps`, `FinishCancellationRestockDeps`,
    `RefundOrderDeps`, `SettleDeps`, `LatePaymentDeps`, `ResolveUnverifiedRefundDeps`,
    `CancelDueIntentsDeps`.

  A build fails to compile until each call site passes one. `Logger` is
  `{ info, warn, error }`, each `(message: string, fields?: Record<string, unknown>) => void`;
  a thin wrapper over `console` is enough. To discard diagnostics on purpose, pass
  `NOOP_LOGGER`; both it and the `Logger` type are exported from `@urumi.ai/otta-domain`.
  Adapter authors using the `@urumi.ai/otta-domain/testing` harnesses must include `logger`
  in `settleDeps` and the other deps they build.
- **Two warnings changed shape** (#655). The cart's `addLine` warning ("could not retire an
  out-of-stock claim") had the error message as a string second argument. It now has
  `{ error: { name, code?, message } }`. The coupon `holdsUseUnderKey` warning (new since 0.1.0)
  logs the same described form, not the raw `Error`. The message is cut to 160 characters
  (with `…` appended), quoted runs and email-shaped text in it are replaced with `<value>`, and
  non-printable or non-ASCII characters with `?`. A log filter or test that matched the old
  arguments must change.
- **Cash on delivery** adds order states, payment methods, failure codes, port methods and
  wire fields. The full list is in
  [ADR-0044](../../adr/0044-cash-on-delivery-is-an-offline-payment-method.md), under
  "Breaking for 0.2.0 consumers". It is not repeated here.
- **Not breaking:** the new `CancelUnpaidOfflineDeps` (cash on delivery) also requires `logger`.

## What a running store sees

- **`@urumi.ai/otta-plugin@0.2.0` needs EmDash `^1.3.1`.** `@urumi.ai/otta-plugin@0.1.0` declared
  no `emdash` peer, so this is new. `@urumi.ai/otta-store@0.2.0` pins EmDash and
  `@emdash-cms/cloudflare` at exactly `1.3.1`. A later release that moves them is covered by
  the paragraph "A release that moves EmDash, Astro or React" at the top of
  [`UPGRADING.md`](../../UPGRADING.md).
- **An unclaimed store needs the setup link** (ADR-0042; the gate is in
  `@urumi.ai/otta-store`'s middleware). Only the holder of the setup token may reach
  `/_emdash/*` (media reads, plugin routes and the health probe aside) until setup is
  finished. `@urumi.ai/otta-store` has no 0.1.0, so this matters only to a store deployed
  from `main` (then `sites/staging`) before the gate (#671) that is part-way through EmDash's
  setup wizard: its next setup request is refused. The wizard's API calls get `403` with
  `SETUP_CLAIM_REQUIRED`, and the admin pages show "This store hasn't been set up yet". To go
  on, open the claim link. With no `OTTA_SETUP_TOKEN` secret, it is written once to Workers
  Logs (or the dev server's console) in a line tagged `[otta-setup]`. With the secret set,
  open `/_emdash/admin/setup?setup_token=` followed by its value. If the log line has aged
  out, set the `OTTA_SETUP_TOKEN` secret (it replaces the generated token) and open that link,
  or read the stored token from D1 as [`DEPLOYMENT.md`](../../DEPLOYMENT.md) §2.2 describes. A
  store whose setup is already finished is not affected.
- **Cash-on-delivery orders hold at most 10 physical items by default** (ADR-0044). Cash on
  delivery is new in 0.2.0, so every store that turns it on gets this cap. The setting is
  `settings:codMaxUnitsPerOrder`, **Most items in one order** under **Store settings →
  General → Cash on delivery**. An order over the cap is refused, and the buyer sees only
  "Cash on delivery isn't available for this order right now". Raise the setting, up to 1000,
  or set it to 0 for no cap.
